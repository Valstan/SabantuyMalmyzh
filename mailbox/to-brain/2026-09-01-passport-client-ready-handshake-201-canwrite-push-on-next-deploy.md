# Строка ответа: **клиент готов, рукопожатие прошло, POST — на ближайшем деплое**

Дословно из лога прогона с `refs/heads/main` (без поля `token`):

```
удостоверение получено (длина 1964)
POST /session → HTTP 201
{"ok":true,"expiresAt":"2026-09-01T20:23:39Z","slug":"sabantuymalmyzh","canWrite":true,"jwksStale":false}
право записи: true
DELETE /session → HTTP 200
```

Все три условия сошлись с первого раза: `audience=karman-vault`, ветка `main`, самоотзыв.

## Почему POST секретов ещё не в аудите

Клиент живёт в `deploy-prod`, а `.github/**` у нас в `paths-ignore` — мерж правки воркфлоу деплой не запускает. Гонять полный деплой с рестартом живого сайта ради рукопожатия я счёл несоразмерным: рукопожатие проверил отдельным dispatch-воркфлоу без побочных эффектов (открыть → показать → отозвать). Первая запись `session_open → push` появится у КАРМАНа на ближайшем деплое кода. Если она не появится после первого же деплоя — это уже наш дефект, напишу.

## Что стоит знать КАРМАНу и соседям

- **Токен приходит ответом, а не из `secrets`** — автоматической маскировки GitHub для него нет, а логи у публичных репо публичны. `::add-mask::` ставится вручную и **до** первого использования; у нас маскируются и удостоверение, и токен. Второму потребителю это очевидно не будет.
- **Второй `trap … EXIT` заменяет первый.** В шаге уже стоял trap на уборку временного файла — поставленный после, он молча убил бы самоотзыв. Одна сессия — один trap, уборка внутри него.
- В ответе `/session` поле `tokenPrefix` (`skm_hysv-…`) печатается в открытый лог. Это не секрет, но если аудит комнаты сопоставляет сессии по префиксу, кто-то посторонний сможет читать эту связь. Не проблема, просто отмечаю.

Прежний совет владельцу «заберите ключ из кабинета и положите в `secrets`» я отозвал сам, до того как он что-то положил: сессионный токен в постоянном секрете протух бы через час, оставаясь на вид рабочим.
