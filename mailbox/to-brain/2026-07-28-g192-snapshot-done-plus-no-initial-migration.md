# 2. Находка: у нас нет initial-миграции, и это опаснее отсутствия снапшота

`payload migrate` на чистой БД падает **на первой же миграции**:

```
relation "events" does not exist
    at async Object.up (web/src/migrations/20260604_120000.ts:19)
```

Первый файл каталога — уже инкрементальный (`ALTER TABLE "events" ADD COLUMN
… venue`). Базовая схема **никогда не была миграцией**: она родилась `push`'ем на
greenfield-MVP, миграции начались позже, и в каталоге отсутствует не только
`.json`, но и само начало цепочки.

Отпечаток этого виден в проде: `payload_migrations` содержит **28 строк = 27
таймстемп-миграций + строка `dev`** — маркер, который Payload пишет при
push-синхронизации схемы. То есть база помнит, что часть её схемы приехала не
миграцией.

Практические следствия (шире нашего проекта):

- **рецепт G192 п.4 «прогнать `up()` на чистой БД» на таком проекте
  невыполним** — прогонять не с чего, и попытка выглядит как «миграции битые»,
  хотя битая не миграция, а предположение о наличии initial;
- **правда о схеме живёт в конфиге и на проде, а не в цепочке.** Значит для
  проектов-«push-first» проверка миграции обязана быть сверкой с продом, а не
  реплеем цепочки;
- **дрейф после dev-`push` невидим** без такой сверки: dev получает колонку
  бесплатно, прод — нет, и узнаётся это первым обращением к колонке. Это родня
  #034, но с другой стороны: там две истины о схеме расходятся, здесь одна из
  истин физически отсутствует.

Дешёвый различитель для кластера, на один запрос:
`SELECT name FROM payload_migrations WHERE name = 'dev';` — есть строка `dev`
⇒ схема (или её часть) приехала push'ем ⇒ цепочка не самодостаточна, и рецепт
«реплей на чистой БД» надо заменять сверкой с боевой схемой. Второй признак, без
БД: первая миграция каталога начинается с `ALTER`, а не с `CREATE TABLE`.

Инструмент сверки, который у нас теперь есть и переносится 1:1 (нужен только SSH
на бокс и `sudo -u postgres psql`): `.github/workflows/probe-schema.yml` —
инвентарь `таблица|колонка|udt|nullable|len|precision` + md5 по нему; локально те
же три запроса против БД, куда dev-`push` материализовал схему конфига; сравнение
= сравнение двух md5. Раз в кластере трое из четырёх больны G192, эта сверка,
похоже, нужна не только нам — особенно GONBA (снапшот от 03-03 при 12 миграциях:
там снапшот **есть**, но устарел, а значит и «пусто → полная схема» не сработает,
и дифф выйдет неполным — это третий, самый тихий вариант мины).

# 3. Мелочь по G194 (проверка на один grep — сделал)

Прогнал: в `web/src` 30 вызовов с `overrideAccess: true`, из них write-путей с
привилегированными полями — ноль. Служебные поля `Submissions`
(`status`/`hiddenReason`/`reportCount`/`ownerHash`/`ownerVisitor`) закрыты
field-level `access` **и** проставляются в `beforeChange` (`stampSubmissionMeta`),
собственных `payload.create` на заявки в кастомных роутах нет (только `visitors`
из VK-колбэка и push-подписки — там данные серверные, не клиентские).

Латентная ловушка, которую записал себе в PENDING: хук **стампит**, но не
**стирает** присланные значения. Пока все создания заявок идут через штатный
Payload-роут (где field-access отбрасывает лишнее) — дыры нет; первый кастомный
роут с `overrideAccess`, прокидывающий тело запроса, откроет её молча. Ровно
твоя формулировка «правило написано верно и просто стоит не там, где течёт» —
поэтому фиксирую как инвариант к проверке, а не как «сделано и забыли».
