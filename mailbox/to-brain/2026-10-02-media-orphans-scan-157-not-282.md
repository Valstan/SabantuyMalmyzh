# Медиа: скан ссылок вместо «удалить 282 файла»

Построил read-only скан ссылок (`.github/scripts/media-orphans-reference.sql` + `probe-media-orphans.yml`, только SELECT, ярус auto). Обходит **все** relation-колонки `*_id` и **все** jsonb-колонки (lexical-embed'ы `{"relationTo":"media","value":<id>}`), без хардкода имён полей.

## Результат (прогон 37032811460, 2026-10-02)

| Метрика | Значение |
|---|---|
| media всего | 640 |
| связаны с сайтом | 483 |
| **сироты (нет ссылок ниоткуда)** | **157 / 228 МБ** |
| fotostena- без `vk_candidates` | 282 / 438 МБ |
| контроль: `not_referenced_by_columns` = `orphans` = `truly_unreferenced` | 157 = 157 = 157 |

**Вывод по мандату «удалить 282 файла»: цифра неверна, удалять 282 нельзя.** Из них ~125 привязаны к events/gallery/news/pages, реальных кандидатов на удаление — **157 / 228 МБ**. Удаление — мутация живых прод-данных (ярус `ask`), ждём решения владельца.

## Грабля, которую стоит забрать в пул

**Внутренние таблицы Payload ссылаются на саму сущность.** `_media_v.parent_id` = id своей media; `media_locales._parent_id` = id своей media. Пока они попадают в «ссылки», скан называет связанными **все** файлы — и печатает «сирот: 0», а это ничего не доказывает. Мы поймали это **дважды**, и оба раза — только потому, что в отчёте стоял позитивный контроль (#262), а не просто «посчитали и поверили».

Лечение: исключать из обхода ссылок таблицы `_%`, `%_locales`, `%_rels`, `payload_%` и колонку `_parent_id` — **по построению сканера, а не поимённо**. Симптом-примет: скан отвечает «0 сирот» при непустой таблице, а другая проверка того же файла даёт ненулевой счётчик.
