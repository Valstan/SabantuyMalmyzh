# Миграции схемы — правила и провенанс снапшота

## Правило №1: `.json`-снапшот коммитится вместе с миграцией (G192)

Drizzle генерирует миграцию как **дифф против последнего `.json`-снапшота в этом
каталоге**, а не против живой БД. Нет снапшота — диффить не с чем, «текущее
состояние» считается **пустым**, и `migrate:create` выдаёт не инкремент, а схему
с нуля: `CREATE TABLE` на все таблицы + `down()` с `DROP TABLE … CASCADE` по всем.
Файл при этом валиден и выглядит правдоподобно — ошибок и предупреждений нет.

Механика (наша версия Payload 3.75):
`@payloadcms/drizzle/dist/utilities/buildCreateMigration.js` — берёт последний
`*.json` каталога (`readdirSync … filter(endsWith('.json')).sort().reverse()[0]`),
при отсутствии подставляет пустой `defaultDrizzleSnapshot`; сам снапшот пишет
строкой `fs.writeFileSync(filePath + '.json', drizzleJsonAfter)` — **только когда
сам генерирует SQL**. Наши 27 миграций писались вручную по push-inspect (#017/R10),
`migrate:create` не вызывался → снапшота не появилось ни одного.

Отсюда дисциплина:

1. **`.ts` + `.sql` + `.json` — три файла одной миграции.** Пара без снапшота = мина
   под следующий автоген.
2. **`down()` читать глазами до применения.** Автогену на слово не верить.
3. Накат на прод — `apply-migration.yml` **с `--ref <feature-branch>`** (G28), до мержа.

## Правило №2: enum расширять пересборкой типа, а не `ADD VALUE` (G193)

Postgres запрещает **использовать** новое значение enum в той же транзакции, где оно
добавлено, а `payload migrate` идёт одной транзакцией. Автоген выдаёт только
`ALTER TYPE … ADD VALUE`; как только в миграцию попадает осмысленный
`UPDATE … SET status='новое'` (перевод существующих строк), она падает — **но
только там, где есть данные**. На чистой схеме `UPDATE` не задевает ни строки,
CI зелёный, узнаётся на проде.

Нас это касается предметно: `enum_registrations_status`,
`enum_vk_candidates_status`, статусы модерации UGC (`submissions.status`,
`submission_comments.status`) — типовые поля, которые расширяются по ходу жизни
продукта, причём уже на боевых данных.

Лечение — пересобрать тип, а не расширять:

```sql
ALTER TABLE "t" ALTER COLUMN "status" SET DATA TYPE text;
UPDATE "t" SET "status" = 'новое' WHERE "status" = 'старое';   -- окно, пока это text
DROP TYPE "public"."enum_t_status";
CREATE TYPE "public"."enum_t_status" AS ENUM (...);            -- с новым набором
ALTER TABLE "t" ALTER COLUMN "status" SET DATA TYPE "public"."enum_t_status"
  USING "status"::"public"."enum_t_status";
```

Симметричный `down` обязателен. Полный разбор — G193 в библиотеке мозга.

## Провенанс `20260705_120000.json`

Снапшот-базлайн, **сгенерирован 2026-07-28** (а не в день миграции `20260705_120000`)
по мандату brain от 2026-07-26 (G192): на тот момент в каталоге было 27 миграций и
**ни одного** снапшота. Имя намеренно совпадает с последней миграцией — снапшот
описывает состояние схемы **после** неё, и совпадение имён делает инвариант
«миграция без снапшота» видимым глазами.

Как получен и что проверено:

- сгенерирован тем же кодовым путём, которым его пишет Payload: `migrate:create`
  против временного локального кластера PG17; сопутствующий полноразмерный `.ts`
  (1270 строк, 73 `CREATE TABLE`, 73 `DROP TABLE … CASCADE` в `down()` — та самая
  мина G192 в нашем масштабе) удалён, `index.ts` восстановлен;
- **снапшот == схема конфига:** повторный `migrate:create` после появления файла
  даёт «No schema changes detected» и не создаёт файлов;
- **схема конфига материализована и сверена по объёму:** dev-`push` в чистую БД →
  73 таблицы / 41 enum, ровно как в снапшоте (`tables: 73`, `enums: 41`).

## Осторожно: цепочка миграций НЕ воспроизводит схему с нуля

Первая миграция каталога (`20260604_120000`) уже инкрементальная
(`ALTER TABLE "events" ADD COLUMN … venue`) — **initial-миграции с базовой схемой в
проекте нет**: схема родилась `push`'ем на greenfield-MVP, миграции начались позже.
Проверено: `payload migrate` на чистой БД падает на первой же миграции
(`relation "events" does not exist`).

Следствия:

- «прогнать `up()` на чистой БД (initial → новая)» из рецепта G192 у нас
  **неприменимо** — прогонять не с чего;
- источник правды о схеме — **конфиг** (`push`) и **живой прод**, а не цепочка;
- сверка «конфиг ↔ прод» делается read-only воркфлоу
  [`probe-schema.yml`](../../../.github/workflows/probe-schema.yml) (инвентарь
  таблиц/колонок/enum'ов + контрольная сумма) — дрейф после dev-`push` иначе
  невидим (родня #034).
