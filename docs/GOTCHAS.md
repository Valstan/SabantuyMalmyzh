## Поиск и аудит

### Слепые пятна грепов: пустой вывод неотличим от чистого результата

У обоих наших инструментов есть слепое пятно, и оба молчат одинаково — `rc=1`, ноль строк.

| Инструмент | Слеп к |
|---|---|
| `grep -i` | кириллице (локаль `C`): `grep -i 'МАЛМЫЖ'` → пусто при наличии строки |
| `rg` | шаблонам с ведущим `/`: MSYS конвертирует такой аргумент в windows-путь до передачи нативному `rg.exe` |

Рабочие формы для путей: `MSYS_NO_PATHCONV=1 rg -F '/etc/foo'` · `rg -F 'etc/foo'` (без ведущего
слеша) · `rg '[/]etc/foo'`. Трюк с `//` **не работает** — проверено. Форма, свободная от обоих
пятен: `git grep -n -e <шаблон>`.

Оба пятна пойманы на себе в один час: латинскую форму имени хостера вычистили, а кириллическую
`grep -i` не показал; следом `rg` вернул ноль по серверным путям, и на этом ложном «чисто» было
опубликовано утверждение, что путей в репо нет. **Смена инструмента не лечит класс — она меняет
слепое пятно.** Отсюда правило канона: метод проверяется на заведомо непустом контроле (pool #262).

### Аудит сверяется со списком, а список никто не пересчитывает

Хост чужой комнаты числился в PENDING как «три места». К моменту чистки их было четыре: четвёртое
завёл тот же сеанс, что писал строку «три места те же, новых вхождений нет», и записал его только
комментарием в коде. Оба источника были правдой на момент написания и разошлись молча.
Проверять надо **значение в дереве**, а не свою же прошлую запись о нём.

## Служебные таблицы Payload

### `payload_locked_documents_rels` — колонка на каждую коллекцию

Payload берёт блокировку при открытии **любого** документа и перечисляет там все коллекции разом.
Ручная миграция, заведшая коллекцию и не добавившая колонку `<slug>_id`, роняет **всю** админку
(«Application error», в журнале `column …_id does not exist`), а не только новый раздел.

Молчит под обычными гейтами: заготовка DDL снимается по именам **новых** таблиц, правка чужой
существующей в неё не попадает; `CREATE TABLE IF NOT EXISTS` для существующей — тихий no-op;
приёмка сравнивает список таблиц, а он не менялся; dry-run в транзакции проверяет выполнимость
SQL, не полноту. Ловится сверкой пары «таблица.колонка» — шаг «Дрейф-проба» в
[`probe-schema.yml`](../.github/workflows/probe-schema.yml).

Класс третий раз на экосистему (G35 → Калинино → РМЗ-сайт, у последнего админка лежала сутки).

### Защитный хук, который фильтрует «по роли», стирает и серверные пересчёты

G194: служебные поля UGC пишет сервер, клиент их задавать не должен. Естественная защита —
хук в `beforeValidate`, стирающий их из `data`, если `req.user` не персонал. Ловушка: **у
серверных пересчётов юзера тоже нет**. `recountViews`/`recountComments`/`recountReactionLikes`/
`applyContentReport` пишут `viewCount`/`likeCount`/`commentCount`/`reportCount` локальным API без
`req.user`, то есть такой хук вычистил бы ровно то, ради чего они существуют: **запись проходит,
ошибки нет, число просто не меняется** (2026-11-01, поймано чтением хука до мержа, PR #409).

Различать источник, а не только роль: `req.payloadAPI` = `'local' | 'REST' | 'GraphQL'`.
Локальный API (наш код: хуки, роуты, сиды) — не трогаем; стрижём только внешние запросы и только
у не-персонала. Роуты, где посетитель меняет служебное поле по своим правилам
(`/api/ugc/delete-submission` ставит `status: 'removed'`), сами проверяют владельца и зовут API
**без** `req` — они остаются `local` и не ломаются.

Обе половины условия закрепить тестом: «слишком широко» — молча умирают счётчики, «слишком
узко» — клиент подменяет статус публикации. Оба отказа не видны ни по коду ответа, ни в логах.

## Сиды на проде (`corepack pnpm -C web payload run …`)

Все три грабли пойманы 2026-10-02–03 на `attach-orphan-photos.yml`; симптом у всех
одинаковый — **воркфлоу зелёный или красный, а по факту ничего не произошло**.

### `payload run` завершает процесс сразу после загрузки модуля

`main().then(...)` в сиде — процесс умирает с кодом 0 и **пустым выводом**: CLI импортирует файл,
модуль «оценил» (асинхронная работа ушла в фон), и всё. Скрипт отработал 10 с и сказал
ничего: ни отчёта, ни ошибки, ни падения. Убило три прогона подряд, пока не сверились
с рабочими сидами — у них `const payload = await getPayload({ config })` **на верхнем уровне**.

Рецепт: сид = top-level `await`, никаких обёрток; проверить локально `payload run <файл>` —
хотя бы строка вывода после `getPayload` обязана появиться.

### `payload run` глушит необрабоянное отклонение верхнего уровня

Симптом: `ELIFECYCLE Command failed with exit code 1` и **ни одного слова о причине**.
`writeSync(2, …)` тоже не спасает: stderr дочернего `pnpm` в логе воркфлоу не виден.

Рецепт: тело сида под общим `try/catch`, причина печатается через `payload.logger.info`
(её видно в логе) — плюс `describe(err)` с `cause`, потому что у ошибок Drizzle
сообщение приезжает многострочным.

### Payload молча выбрасывает невалидные значения — «готово» ≠ записано

`Gallery.photos` — это `type: 'array'` с блоком `{ image, caption }`, а не hasMany-связь.
Скрипт передал `[...existing, 12345, 12346]` (список id), Payload **выбросил невалидные
значения без ошибки**, вернул успех, скрипт отрапортовал «добавлено 110 фото» — альбом
остался с 9. Поймала только внешняя приёмка (`psql … gallery_photos` → 9 вместо 119).

Рецепт: **после любой записи в коллекцию перечитать её и сравнить с ожиданием**, иначе
`throw`, если не выросла. Плюс правило: тип поля проверять по `src/collections/*.ts`,
а не по форме таблицы — join-таблица `gallery_photos` выглядит как hasMany и это ловушка.

### `ssh host cmd arg1 arg2 …` склеивает аргументы БЕЗ кавычек

`ssh sabantuy 'bash -s' main apply 1 sabantuy-2026 "Сабантуй 2026 в Малмыже. Как это было" 2026-07-04`
доезжает до удалённой стороны как **одна строка без кавычек**: пробелы в заголовке
разбили его на слова, и `$6` оказался первым словом заголовка — «2026» вместо
`2026-07-04`. Payload такую дату не отвергает, падение пришло из Postgres уже на записи
(`invalid input syntax for type timestamp …: "2026"`).

Тот же приём объясняет, почему `attach-orphan-photos.yml` работает: там все параметры
без пробелов (ref, режим, slug, id). Это везение, а не защита.

Рецепт: параметры пакуются в **один base64-блок** и разбираются на боксе через
`mapfile -t ARGS < <(printf '%s' "$1" | base64 -d)` с проверкой их количества. Бонус —
кириллица не теряет кодировку на трёх слоях (раннер → ssh → удалённый bash).

### Блок массива Payload несёт собственный `id` — при переносе он конфликтует

Блок `{ image, caption }`, прочитанный из альбома галереи, приходит с `id` — это
идентификатор строки в таблице `gallery_photos`. Скопировать такие блоки в **новый**
альбом нельзя: `ValidationError: The following field is invalid: id` (уникальный ключ).
Нас интересуют картинка и подпись — блок пересобирается заново.

### `CREATE TEMP TABLE` + `drizzle.execute` = temp-таблица не доживает до следующего запроса

Каждый `execute` берёт **своё соединение из пула**, а temp-таблица живёт в соединении.
След: блоки `DO $$ … EXCEPTION WHEN others THEN NULL` глотали «relation does not exist»
и рапортовали успех, а `SELECT` видел пустую таблицу → «сирот: 640», то есть **все** файлы.

Рецепт: скан строить **одним** запросом (`WITH ref AS (SELECT … UNION ALL SELECT …)`),
без temp-таблиц; и стоп-контроль в самом скрипте: если «сироты» == все файлы — выходим
с ошибкой, а не публикуем.

## Бокс и nginx

### Снял `default_server` — и отдал свою публичку чужому блоку

2026-11-01 (шаг по цепочке #251/444): снял слово `default_server` со своего `:80`-блока,
проверил `nginx -t` и `systemctl reload` — зелено. Через минуту снаружи открывался
**соседский сайт**: 200, валидный HTML, живая вёрстка.

Корень: у нашего публичного блока стоял ровно `server_name _` — своих имён в нём **не было**,
вся публичка висела на дефолте. «Имена отвечают маркерами» проходило **через сам
`default_server`**, а не через явное совпадение. Снял флаг → дефолтным на `:80` стал первый
блок в `conf.d` по алфавиту — чужой.

Рецепт: перед снятием флага доказать, что имена перечислены явно
(`nginx -T | grep -A2 'listen 80' | grep server_name` по своему файлу); нет имён — сначала
дописать `server_name _ <свои имена>;`, потом снимать флаг. И приёмка **по `<title>`, а не по
коду ответа**: `curl -H 'Host: <свой домен>' http://127.0.0.1/` вернёт 200 и от чужого блока —
код ответа этот отказ не показывает.

## Секреты и CI

### Перевёл литерал в `secrets.X` — проверь, что `X` вообще заведён

2026-10-02: рефакторинг D-038 заменил 21 копию `BASE=<путь на боксе>` на `secrets.DEPLOY_BASE`
(PR #360) ради того, чтобы убрать литерал из отслеживаемых файлов. Секрета `DEPLOY_BASE`
в репозитории **не было** — GitHub молча подставил пустую строку, `BASE=` уехал на бокс
пустым, и `deploy-prod` падал до `mkdir` (обычно это был бы `rm -rf /releases/…`).
Сломалось всё, что печатает на боксе: деплой, все сиды, `collect-vk`, `moderate-vk`,
`sync-media-to-s3`, `recover-*`. Починилcь само по себе только когда значение положили
в секрет руками (взяли из истории, литерал там остался).

Рецепт: после такого рефакторинга — `gh secret list` и **один прогон воркфлоу глазами**:
в логе должно быть `BASE=/…`, а не `BASE=`. Плюс проверка `[ -n "$BASE" ] || { echo "::error::…"; exit 1; }`
сразу после присваивания — иначе пустой секрет выглядит как «непонятный Permission denied
в другом месте».

### Сигнал «красный прогон открывает issue» ломается в трёх строках — и это видно только красным прогоном

`deps-audit` был красным 17 дней не из-за уязвимостей, а потому что падение по расписанию
не приходит никому: его видно только тому, кто откроет вкладку Actions. Завели job `notify`
(issue с меткой, повторный красный — комментарий) и вход `force_fail` в `workflow_dispatch`,
чтобы показать сигнал намеренно. **Первый же красный прогон показал, что сигнал не работает:**

- `gh` в job **без `actions/checkout`** падает на `fatal: not a git repository`. Достаточно
  `-R "${GITHUB_REPOSITORY}"` у **каждого** вызова — но одного пропущенного хватает: у нас
  `-R` не было ровно у `gh label create`, и job умирал до открытия issue;
- `${{ github.run_started_at }}` в момент старта job **пуст** → дата в заголовке и в теле
  оказалась бы пустой. Брать время на месте (`date -u +%Y-%m-%dT%H:%M:%SZ`), не из контекста;
- метка должна **существовать до** `gh issue create --label` — `gh label create --force -R …`
  отдельным вызовом выше.

По коду всё три выглядели правильно. Правило «гейт считается заведённым, когда показан его
красный» (ревизия #104) распространяется и на **сигнал об ошибке**: пока ветка «открыть issue»
не прогонялась, это утверждение, а не механизм.

## Сборка и деплой

### Деплой падает на `next/font` — это сеть, а не код

2026-11-01: `deploy-prod` упал на шаге `Build (standalone)` с

```
src/app/(frontend)/layout.tsx
An error occurred in `next/font`.
TypeError: Cannot read properties of null (reading '1')
  at next/dist/compiled/@next/font/dist/google/loader.js:122
```

Код тут ни при чём: `next/font/google` **на этапе сборки** ходит на `fonts.googleapis.com`
за CSS и `.woff2`. Ответ не в ожидаемом формате (лимит, капча, обрыв) — и падает сборка.
Тот же коммит собрался успешно за 40 минут до этого, повторный прогон через 40 минут после —
тоже. То есть это транзиентный отказ, и **`rerun --failed` его лечит**.

Что важно помнить: красный деплой **не выкатывает новую версию** (активация после сборки),
прод остаётся на предыдущей. Проверять надо не «упало ли», а «какая версия на проде».

**Закрыто 2026-11-01.** Шрифты переехали в репозиторий: `web/public/fonts/*.woff2` (четыре
файла, ~98 КБ) + `@font-face` руками в `web/src/app/(frontend)/fonts.css`. Взяты **вариативные**
сабсеты (`Manrope` 400..700, `Playfair Display` 700..900), поэтому один файл на семейство-сабсет
вместо файла на каждый вес: 4 вместо 14.

Три вещи, на которых легко ошибиться при таком переезде:

- **`unicode-range` обязателен.** Кириллица и латиница — разные файлы, и **цифры живут в
  латинском** (кириллический сабсет не содержит `0-9`). Без `unicode-range` два `@font-face`
  одного семейства перекрывают друг друга и кириллица проваливается в фолбэк. Значения — не по
  памяти, а из ответа Google CSS API: `curl -H 'User-Agent: <Chrome>' 'https://fonts.googleapis.com/css2?family=Manrope:wght@400..700&display=swap'`.
- **`next/font` больше не preload'ит** — прелоад писал он. Без него браузер узнаёт о файлах
  только из CSS, то есть после первой отрисовки. Вернули руками: `<link rel="preload" as="font"
  type="font/woff2" … crossOrigin="anonymous">` в layout — React 19 поднимает их в `<head>`
  (проверено в собранном `.next/server/app/index.html`, не на веру).
- **Файлы в `public/` не получают длинный кэш сами.** `/_next/static/*` едет с `immutable`, а
  `public/` отдаётся `max-age=0`. Своя папка добавляется в список `STATIC` в `next.config.js`
  (`/afisha`, `/decor`, `/icons`, теперь `/fonts`).

### «Кириллический сабсет» ≠ все кириллические буквы: татарские `ә ө ү ң һ җ` в него не входят

Проверено 2026-11-01, когда шрифты переезжали в репозиторий. Google отдаёт для Manrope
`cyrillic` с диапазоном `U+0301, U+0400-045F, U+0490-0491, U+04B0-04B1, U+2116` — шесть
татарских букв (`ә` U+04D9, `ө` U+04E9, `ү` U+04AF, `ң` U+04A3, `һ` U+04BB, `җ` U+0497) в
него **не попадают**, и это не мелочь для сайта на двух языках.

Расширение не спасает: `cyrillic-ext` объявляет `U+0460-052F`, то есть **обещает** эти буквы
по диапазону, но в файле их нет — глифы отсутствуют, браузер отдаёт их следующему шрифту
стека. Второй файл `+25 КБ` покупает покрытие только для `ү ө һ` (три из шести), поэтому
`cyrillic-ext` **не подключён**; у Playfair Display его Google вообще не публикует.

Итог: татарский текст рисуется **фолбэком** (`Georgia, …` / системный sans) на трёх буквах
и на `ә ң җ` — на всех. Это сознательно принятая неполнота, а не недосмотр: альтернатива —
свой шрифт с полным покрытием, отдельная работа.

**Как проверять покрытие.** Сравнением ширины одного символа двумя стеками, где первый —
испытуемый шрифт, второй — заведомо другой (`monospace` против `serif`): совпало — глиф взят из
фолбэка. Обязателен **положительный контроль**: строка из букв, которые точно есть
(`'абвгдй'` → ширина та же), и отрицательный (`'abcde'` на шрифте без латиницы → разная).

Две ловушки метода:

- **пробел в пробной строке делает тест бессмысленным** — пробел вне кириллического диапазона,
  ширины разойдутся на нём, а не на букве, и вывод получится «всё покрыто»;
- мерить надо **по одному символу** (или `measureText` двух алфавитов с известными различиями),
  иначе один непокрытый символ маскирует остальные в общей ширине.

### `headers()` в `next.config.js` запекается в манифест — без пересборки правка не действует

Добавил `/fonts` в список кэш-правил **после** сборки, запустил `next start` — файлы отдаются с
`max-age=0`, как будто правила нет. Причина: `headers()` попадает в `.next/routes-manifest.json`
на этапе `next build`, а `next start` читает **манифест**, не живой конфиг. Проверка одной
командой (и единственный способ увидеть это до прода):

```bash
node -e "console.log(require('./web/.next/routes-manifest.json').headers.map(h=>h.source).join('\n'))"
```

Нет нужного `source` — правило не работает, сколько бы раз ты его ни правил. То же касается
`redirects()` и `rewrites()`: все три живут в манифесте сборки.

## Зависимости и аудит

### Override поверх мажора родителя: типы врут в одну сторону, рантайм в другую

`@payloadcms/email-nodemailer` объявляет `transportOptions` как `SMTPConnection.Options`
(в нём `auth` **нет**), но отдаёт объект прямо в `nodemailer.createTransport()`, который ждёт
`SMTPTransport.Options` (там `auth` **есть**). Пока стоял `nodemailer` 9, типы совпадали случайно;
после override 9→10 `typecheck` упал на `auth` — **в коде, который работает**.

Грабли: падение типа здесь читается как «override сломал адаптер», хотя сломался только
объявленный тип. Проверять надо рантайм, а не тип: тест на живом SMTP-сервере
(`createTransport({host, port, secure, auth})`, заглушка отвечает `250-AUTH PLAIN LOGIN`)
показал, что `AUTH PLAIN` приходит с нашими кредами, письмо доходит целиком.

Ещё грабли: у `web` **нет прямой зависимости** на `nodemailer` (strict linking pnpm), поэтому
импортировать его тип в конфиг неоткуда — каст сужаем до типа, который объявляет сам адаптер
(`Parameters<typeof nodemailerAdapter>[0]['transportOptions']`), и пишем рядом, что снимать его
надо при расширении типа у апстрима. Временный смоук-скрипт кладём внутрь `web/`
(резолв ESM идёт от файла, не от cwd) и удаляем после — в `.pnpm`-путь импорт писать можно,
но жить ему в репозитории незачем.

### Аудит меряем тем же прибором, что и гейт

`pnpm audit` из корня репо и `pnpm audit --prod` из `web/` дают **разные наборы**: письмо brain
говорило 41 уязвимость и 7 high, гейт с `--prod --audit-level=high` — 1 critical и 14 high.
Смотреть надо ту команду, что стоит в `deps-audit.yml`, в том же каталоге. Иначе чинишь не то,
что красное, и отчитываешься числами другого прибора.

## Детекторы схемы

### Детектор «конфиг ↔ БД» видит только ту конфигурацию, в которой запущен

`payload generate:types` (и `migrate:create`) строят схему из конфига **в текущем окружении**.
Плагин, включаемый по env (`s3Storage({ enabled: Boolean(S3_BUCKET && …) })`), локально
выключен, его поля в конфиг не попадают, диф типов чистый, а прод падает на
`column media._objectkey does not exist` (Payload 3.90, 2026-09-21: юнит active, страницы 200,
`/api/media` 500, `/fotostena` пустая; поймал только смоук деплоя по симптому).

Рецепт: детектор гонять с фиктивными значениями **всех** условных плагинов:
`S3_BUCKET=x S3_ACCESS_KEY_ID=x S3_SECRET_ACCESS_KEY=x pnpm generate:types`, диф читать как
«в БД нужна колонка». Список условных плагинов: `grep -n 'enabled:' web/src/payload.config.ts`.

**Второй вход в ту же граблю — обычный `pnpm dev`.** Payload перегенерирует `payload-types.ts`
сам при старте, тем же локальным конфигом. 2026-11-01 после запуска dev под смоук `git status`
показал `M web/src/payload-types.ts` с двумя удалениями — `_objectKey` из `Media` и из
`MediaSelect`. Это **не** улучшение схемы, а тот самый выключенный S3-плагин; коммитить нельзя,
команда — `git checkout -- web/src/payload-types.ts`. Проверять диф этого файла глазами до
`git add`: он единственный в репозитории, который генерируется, и поэтому «изменился сам».

## Машина разработчика

### Git Bash на Windows переписывает аргументы, похожие на POSIX-пути

MSYS конвертирует POSIX-путь в аргументах команд в путь под каталогом установки Git (`C:/Program Files/Git/…`) (2026-09-21:
`gh workflow run cleanup-box.yml -f targets=<абсолютный путь на боксе>` — первый путь уехал на бокс с виндовым
префиксом, второй и третий, после `\n`, остались как есть). Воркфлоу отверг список до первого
`rm` — иначе удаление пошло бы по двум путям из трёх молча.

Рецепт: `export MSYS_NO_PATHCONV=1` перед командой с путями бокса; в воркфлоу — проверять
каждый путь по форме до первого действия, а не по ходу.
