## Поиск и аудит

### Слепые пятна грепов: пустой вывод неотличим от чистого результата

У обоих наших инструментов есть слепое пятно, и оба молчат одинаково — `rc=1`, ноль строк.

| Инструмент | Слеп к |
|---|---|
| `grep -i` | кириллице (локаль `C`): `grep -i 'МАЛМЫЖ'` → пусто при наличии строки |
| `rg` | шаблонам с ведущим `/`: MSYS конвертирует такой аргумент в windows-путь до передачи нативному `rg.exe` |

Рабочие формы для путей: `MSYS_NO_PATHCONV=1 rg -F '/etc/foo'` · `rg -F 'etc/foo'` (без ведущего
слеша) · `rg '[/]etc/foo'`. Трюк с `//` **не работает** — проверено. Форма, свободная от обоих
пятен: `git grep -n -e <шаблон>`.

Оба пятна пойманы на себе в один час: латинскую форму имени хостера вычистили, а кириллическую
`grep -i` не показал; следом `rg` вернул ноль по серверным путям, и на этом ложном «чисто» было
опубликовано утверждение, что путей в репо нет. **Смена инструмента не лечит класс — она меняет
слепое пятно.** Отсюда правило канона: метод проверяется на заведомо непустом контроле (pool #262).

### Аудит сверяется со списком, а список никто не пересчитывает

Хост чужой комнаты числился в PENDING как «три места». К моменту чистки их было четыре: четвёртое
завёл тот же сеанс, что писал строку «три места те же, новых вхождений нет», и записал его только
комментарием в коде. Оба источника были правдой на момент написания и разошлись молча.
Проверять надо **значение в дереве**, а не свою же прошлую запись о нём.

## Служебные таблицы Payload

### `payload_locked_documents_rels` — колонка на каждую коллекцию

Payload берёт блокировку при открытии **любого** документа и перечисляет там все коллекции разом.
Ручная миграция, заведшая коллекцию и не добавившая колонку `<slug>_id`, роняет **всю** админку
(«Application error», в журнале `column …_id does not exist`), а не только новый раздел.

Молчит под обычными гейтами: заготовка DDL снимается по именам **новых** таблиц, правка чужой
существующей в неё не попадает; `CREATE TABLE IF NOT EXISTS` для существующей — тихий no-op;
приёмка сравнивает список таблиц, а он не менялся; dry-run в транзакции проверяет выполнимость
SQL, не полноту. Ловится сверкой пары «таблица.колонка» — шаг «Дрейф-проба» в
[`probe-schema.yml`](../.github/workflows/probe-schema.yml).

Класс третий раз на экосистему (G35 → Калинино → РМЗ-сайт, у последнего админка лежала сутки).

## Сиды на проде (`corepack pnpm -C web payload run …`)

Все три грабли пойманы 2026-10-02–03 на `attach-orphan-photos.yml`; симптом у всех
одинаковый — **воркфлоу зелёный или красный, а по факту ничего не произошло**.

### `payload run` завершает процесс сразу после загрузки модуля

`main().then(...)` в сиде — процесс умирает с кодом 0 и **пустым выводом**: CLI импортирует файл,
модуль «оценил» (асинхронная работа ушла в фон), и всё. Скрипт отработал 10 с и сказал
ничего: ни отчёта, ни ошибки, ни падения. Убило три прогона подряд, пока не сверились
с рабочими сидами — у них `const payload = await getPayload({ config })` **на верхнем уровне**.

Рецепт: сид = top-level `await`, никаких обёрток; проверить локально `payload run <файл>` —
хотя бы строка вывода после `getPayload` обязана появиться.

### `payload run` глушит необрабоянное отклонение верхнего уровня

Симптом: `ELIFECYCLE Command failed with exit code 1` и **ни одного слова о причине**.
`writeSync(2, …)` тоже не спасает: stderr дочернего `pnpm` в логе воркфлоу не виден.

Рецепт: тело сида под общим `try/catch`, причина печатается через `payload.logger.info`
(её видно в логе) — плюс `describe(err)` с `cause`, потому что у ошибок Drizzle
сообщение приезжает многострочным.

### Payload молча выбрасывает невалидные значения — «готово» ≠ записано

`Gallery.photos` — это `type: 'array'` с блоком `{ image, caption }`, а не hasMany-связь.
Скрипт передал `[...existing, 12345, 12346]` (список id), Payload **выбросил невалидные
значения без ошибки**, вернул успех, скрипт отрапортовал «добавлено 110 фото» — альбом
остался с 9. Поймала только внешняя приёмка (`psql … gallery_photos` → 9 вместо 119).

Рецепт: **после любой записи в коллекцию перечитать её и сравнить с ожиданием**, иначе
`throw`, если не выросла. Плюс правило: тип поля проверять по `src/collections/*.ts`,
а не по форме таблицы — join-таблица `gallery_photos` выглядит как hasMany и это ловушка.

### `ssh host cmd arg1 arg2 …` склеивает аргументы БЕЗ кавычек

`ssh sabantuy 'bash -s' main apply 1 sabantuy-2026 "Сабантуй 2026 в Малмыже. Как это было" 2026-07-04`
доезжает до удалённой стороны как **одна строка без кавычек**: пробелы в заголовке
разбили его на слова, и `$6` оказался первым словом заголовка — «2026» вместо
`2026-07-04`. Payload такую дату не отвергает, падение пришло из Postgres уже на записи
(`invalid input syntax for type timestamp …: "2026"`).

Тот же приём объясняет, почему `attach-orphan-photos.yml` работает: там все параметры
без пробелов (ref, режим, slug, id). Это везение, а не защита.

Рецепт: параметры пакуются в **один base64-блок** и разбираются на боксе через
`mapfile -t ARGS < <(printf '%s' "$1" | base64 -d)` с проверкой их количества. Бонус —
кириллица не теряет кодировку на трёх слоях (раннер → ssh → удалённый bash).

### Блок массива Payload несёт собственный `id` — при переносе он конфликтует

Блок `{ image, caption }`, прочитанный из альбома галереи, приходит с `id` — это
идентификатор строки в таблице `gallery_photos`. Скопировать такие блоки в **новый**
альбом нельзя: `ValidationError: The following field is invalid: id` (уникальный ключ).
Нас интересуют картинка и подпись — блок пересобирается заново.

### `CREATE TEMP TABLE` + `drizzle.execute` = temp-таблица не доживает до следующего запроса

Каждый `execute` берёт **своё соединение из пула**, а temp-таблица живёт в соединении.
След: блоки `DO $$ … EXCEPTION WHEN others THEN NULL` глотали «relation does not exist»
и рапортовали успех, а `SELECT` видел пустую таблицу → «сирот: 640», то есть **все** файлы.

Рецепт: скан строить **одним** запросом (`WITH ref AS (SELECT … UNION ALL SELECT …)`),
без temp-таблиц; и стоп-контроль в самом скрипте: если «сироты» == все файлы — выходим
с ошибкой, а не публикуем.

## Секреты и CI

### Перевёл литерал в `secrets.X` — проверь, что `X` вообще заведён

2026-10-02: рефакторинг D-038 заменил 21 копию `BASE=<путь на боксе>` на `secrets.DEPLOY_BASE`
(PR #360) ради того, чтобы убрать литерал из отслеживаемых файлов. Секрета `DEPLOY_BASE`
в репозитории **не было** — GitHub молча подставил пустую строку, `BASE=` уехал на бокс
пустым, и `deploy-prod` падал до `mkdir` (обычно это был бы `rm -rf /releases/…`).
Сломалось всё, что печатает на боксе: деплой, все сиды, `collect-vk`, `moderate-vk`,
`sync-media-to-s3`, `recover-*`. Починилcь само по себе только когда значение положили
в секрет руками (взяли из истории, литерал там остался).

Рецепт: после такого рефакторинга — `gh secret list` и **один прогон воркфлоу глазами**:
в логе должно быть `BASE=/…`, а не `BASE=`. Плюс проверка `[ -n "$BASE" ] || { echo "::error::…"; exit 1; }`
сразу после присваивания — иначе пустой секрет выглядит как «непонятный Permission denied
в другом месте».

## Детекторы схемы

### Детектор «конфиг ↔ БД» видит только ту конфигурацию, в которой запущен

`payload generate:types` (и `migrate:create`) строят схему из конфига **в текущем окружении**.
Плагин, включаемый по env (`s3Storage({ enabled: Boolean(S3_BUCKET && …) })`), локально
выключен, его поля в конфиг не попадают, диф типов чистый, а прод падает на
`column media._objectkey does not exist` (Payload 3.90, 2026-09-21: юнит active, страницы 200,
`/api/media` 500, `/fotostena` пустая; поймал только смоук деплоя по симптому).

Рецепт: детектор гонять с фиктивными значениями **всех** условных плагинов:
`S3_BUCKET=x S3_ACCESS_KEY_ID=x S3_SECRET_ACCESS_KEY=x pnpm generate:types`, диф читать как
«в БД нужна колонка». Список условных плагинов: `grep -n 'enabled:' web/src/payload.config.ts`.

## Машина разработчика

### Git Bash на Windows переписывает аргументы, похожие на POSIX-пути

MSYS конвертирует POSIX-путь в аргументах команд в путь под каталогом установки Git (`C:/Program Files/Git/…`) (2026-09-21:
`gh workflow run cleanup-box.yml -f targets=<абсолютный путь на боксе>` — первый путь уехал на бокс с виндовым
префиксом, второй и третий, после `\n`, остались как есть). Воркфлоу отверг список до первого
`rm` — иначе удаление пошло бы по двум путям из трёх молча.

Рецепт: `export MSYS_NO_PATHCONV=1` перед командой с путями бокса; в воркфлоу — проверять
каждый путь по форме до первого действия, а не по ходу.
